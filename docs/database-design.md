# Database design

## Ownership and conventions

The payment and ledger services have separate PostgreSQL schemas and separate database roles in production. Foreign keys are only enforced within the owning service database; cross-service references are UUID values validated through events or service APIs. Every primary key is a UUID generated by the application. Amounts are `numeric(19,4)` and currencies use ISO-4217 `char(3)`. All event and business timestamps use `timestamptz` in UTC.

`created_at` is immutable. Tables with mutable workflows also expose `updated_at` and an optimistic-lock `version`. Status values will be PostgreSQL enums or constrained text values when migrations are introduced in task 09.

## Payment service schema

### `users`

| Column | Type | Notes |
| --- | --- | --- |
| `id` | UUID PK | User identifier |
| `email` | varchar(320) | Canonical, case-insensitive unique login/contact value |
| `display_name` | varchar(200) | Customer or merchant name |
| `status` | user status | `ACTIVE`, `SUSPENDED`, `CLOSED` |
| `created_at` | timestamptz | Creation time |
| `updated_at` | timestamptz | Last change |

### `accounts`

| Column | Type | Notes |
| --- | --- | --- |
| `id` | UUID PK | Account identifier used by payments and ledger entries |
| `user_id` | UUID | Owning user reference; indexed |
| `currency` | char(3) | Account's settlement currency |
| `status` | account status | `ACTIVE`, `FROZEN`, `CLOSED` |
| `available_balance` | numeric(19,4) | Read model/cache; not the financial source of truth |
| `version` | bigint | Optimistic concurrency version |
| `created_at`, `updated_at` | timestamptz | Audit fields |

An account has exactly one currency. A future multi-currency wallet is modeled as multiple accounts rather than a mixed-currency balance.

### `payments`

| Column | Type | Notes |
| --- | --- | --- |
| `id` | UUID PK | Payment identifier and Kafka partition key |
| `payer_account_id` | UUID | Debited account; indexed |
| `payee_account_id` | UUID | Credited account; indexed |
| `amount` | numeric(19,4) | Positive requested amount |
| `currency` | char(3) | Must match settlement accounts |
| `merchant_reference` | varchar(128) | Client/business reference |
| `status` | payment status | Lifecycle state |
| `failure_code` | varchar(64), nullable | Machine-readable terminal failure |
| `idempotency_key` | varchar(255) | Links to the idempotency record |
| `created_at`, `updated_at` | timestamptz | Audit fields |
| `version` | bigint | Optimistic concurrency version |

Required access paths are `payments(payer_account_id, created_at desc)`, `payments(payee_account_id, created_at desc)`, and a unique merchant reference scoped to the merchant/account when that business rule is enabled.

### `payment_attempts`

Each external processor attempt is recorded rather than overwriting a payment.

| Column | Type | Notes |
| --- | --- | --- |
| `id` | UUID PK | Attempt identifier |
| `payment_id` | UUID | Payment reference; indexed |
| `attempt_number` | integer | Starts at 1; unique per payment |
| `status` | attempt status | `STARTED`, `SUCCEEDED`, `FAILED`, `TIMED_OUT` |
| `processor_reference` | varchar(128), nullable | Provider correlation ID |
| `failure_code` | varchar(64), nullable | Retry decision input |
| `started_at`, `completed_at` | timestamptz | Execution interval |

### `refunds`

| Column | Type | Notes |
| --- | --- | --- |
| `id` | UUID PK | Refund identifier |
| `payment_id` | UUID | Original payment; indexed |
| `amount` | numeric(19,4) | Positive partial or full amount |
| `currency` | char(3) | Must equal the payment currency |
| `status` | refund status | `CREATED`, `COMPLETED`, `FAILED`, `REVERSED` |
| `reference` | varchar(128) | Client-visible refund reference |
| `created_at`, `updated_at` | timestamptz | Audit fields |

Refund totals are validated against the original completed amount transactionally; the concrete database constraint and locking strategy are task 11 and task 26 work.

### `idempotency_records`

| Column | Type | Notes |
| --- | --- | --- |
| `id` | UUID PK | Record identifier |
| `scope` | varchar(64) | API operation, e.g. `CREATE_PAYMENT` |
| `idempotency_key` | varchar(255) | Client-supplied key |
| `request_hash` | char(64) | SHA-256 of canonical request body |
| `payment_id` | UUID, nullable | Resulting payment reference |
| `response_status` | integer, nullable | Cached HTTP response status |
| `response_body` | jsonb, nullable | Cached safe response payload |
| `state` | idempotency status | `IN_PROGRESS`, `COMPLETED`, `FAILED` |
| `expires_at` | timestamptz | Retention boundary |
| `created_at`, `updated_at` | timestamptz | Audit fields |

The uniqueness boundary is `(scope, idempotency_key)`. A reused key with a different `request_hash` is rejected, not replayed.

## Ledger service schema

The ledger is append-only. Corrections are new compensating transactions, never updates or deletes to posted entries.

### `ledger_transactions`

| Column | Type | Notes |
| --- | --- | --- |
| `id` | UUID PK | Transaction/journal identifier |
| `reference_type` | varchar(32) | `PAYMENT`, `REFUND`, `REVERSAL`, `ADJUSTMENT` |
| `reference_id` | UUID | Source payment/refund/event identifier |
| `status` | ledger status | `PENDING`, `POSTED`, `REVERSED` |
| `description` | varchar(255) | Human-readable audit context |
| `occurred_at` | timestamptz | Financial effective time |
| `created_at` | timestamptz | Append time |

`(reference_type, reference_id)` is unique for idempotent event consumption. An explicit reversal has its own transaction and points to the original through `reversal_of_transaction_id`.

### `ledger_entries`

| Column | Type | Notes |
| --- | --- | --- |
| `id` | UUID PK | Entry identifier |
| `transaction_id` | UUID | Parent ledger transaction; indexed |
| `account_id` | UUID | Account affected; indexed with `created_at` |
| `direction` | entry direction | `DEBIT` or `CREDIT` |
| `amount` | numeric(19,4) | Positive amount only |
| `currency` | char(3) | Currency of the entry |
| `status` | entry status | Mirrors posting lifecycle |
| `created_at` | timestamptz | Append time |

For each posted transaction and currency, the sum of debit entries must equal the sum of credit entries. A payment normally produces one debit entry for the payer and one credit entry for the payee; fees use additional balanced entries. `ledger_entries(account_id, created_at desc, id desc)` supports transaction history and balance projection rebuilds.

### `account_balance_projections`

| Column | Type | Notes |
| --- | --- | --- |
| `account_id`, `currency` | composite PK | Projected account balance key |
| `available_balance` | numeric(19,4) | Derived read model |
| `posted_balance` | numeric(19,4) | Sum of posted entries |
| `last_entry_id` | UUID | Projection checkpoint |
| `updated_at` | timestamptz | Projection update time |
| `version` | bigint | Concurrency control |

This projection is rebuildable from `ledger_entries`; it never replaces the immutable ledger as the audit record.
